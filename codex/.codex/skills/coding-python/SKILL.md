# Coding Guidelines (FAKPy)

Keep this skill concise. It summarizes the essential rules for Python/Django work in this repo.

## Stack
- Python 3.12
- Django 5.2.x
- Dependencies via `uv` and `justfile`

## General Style
- Prefer short, readable lines and type hints when possible.
- Indentation: 4 spaces.
- Avoid Unicode unless necessary.
- User-facing Portuguese strings must keep proper accents.
- Repo docs should keep proper Portuguese accents.

## Imports and Enums
- Always include `from __future__ import annotations` in Python files (except autogenerated migrations).
- Import datetime as `import datetime` (do not import members).
- For `choices`, prefer `StrEnum`/`IntEnum` without `Enum` suffix.
- Keep a separate `*Choices` class for field choices.
- Use enums directly (avoid `.value` unless required).

## Constants
- Prefer library constants (e.g., `http.HTTPStatus`).
- Place domain constants near usage:
  - Value objects/fields in their module.
  - Service/domain constants in the service/module file.
  - Migration data constants in the migration.
- In tests, define constants at the top of the test file.
- Avoid global constants modules unless reused in multiple domain modules.
- Use `UPPER_SNAKE_CASE` names.

## Services
- One service per file; filename must match the function name.
- File contains only the service function, DTOs, and local helpers.
- Services must not access ORM directly (`objects`, `filter`, etc.).
- Services call model methods for reads/writes.
- Standard returns:
  - Commands: `CommandResult` (alias in `core.types`).
  - Queries: `QueryResult[DTO]` with `@dataclass(frozen=True)`.
- Expected errors are user-facing messages; views must not log them.
- Exceptions:
  - `RuntimeError`: log with context and redirect to login.
  - Other exceptions: log and follow the 500 handler flow.

## Views
- One view class per file; subclass `View`.
- Each view defines `_render_template`.
- Views never access models directly; call services.
- Wrap service calls in `try/except` only to catch exceptions.
- Validate `err` outside `try/except` blocks.
- `page_subtitle` should mirror menu descriptions in app `__init__.py`.
- Subtitle should derive from the service user story to keep UI/docs consistent.
- POST flow:
  - Success: log `info` and redirect.
  - Expected error: `_render_template` with message.
  - `RuntimeError`: log, flush session, redirect to login.
  - Other errors: log (Rollbar if configured) and let 500 handler run.

## Models
- Provide static/instance methods for queries and writes.
- Group fields by sections (when explicit PKs exist):
  - Identifier, Natural Keys, Main Data, Complementary Data, Model State, Audit Data.

## URLs and State
- Each app defines routes in `src/<app>/urls.py`.
- `src/config/urls.py` only includes app routes and global routes.
- Use `{% url %}` for internal links; avoid hardcoded `href="/..."`.
- Prefer `RedirectView` with `pattern_name` or `reverse()`.
- URLs must be shareable and stateful:
  - Path = resource/hierarchy
  - Query = filters/sort/pagination
  - Fragment = local navigation
- Omit defaults from URLs; UI assumes defaults.
- Never place sensitive data in URLs.
- Use `pushState` for navigable changes, `replaceState` for frequent refinements.
- Keep drafts/modals/scroll out of URLs.

## Date Fields (UI)
- Use `type="text"`, `inputmode="numeric"`, mask `00/00/0000`.
- Add `js-datepicker` class.
- Keep `input_formats=["%d/%m/%Y"]` in `DateField`.
- Datepicker is initialized via `FAK.forms.registrarDatepicker(".js-datepicker")` in `base.html`.

## Logging
- Use `logger = logging.getLogger(__name__)` per module.
- Log `info` for successful POSTs before redirect.
- Do not log expected errors from services.
- Log `RuntimeError` with context and redirect to login.
- Log unexpected exceptions and allow 500 handler.
- Use `core.middleware.request_logging.context.update(...)` for request context.
- Prefer `log_message` and `log_level` fields; send only `log_message` when sufficient.

## Validation
- Models: local integrity and invariants (`clean`, methods).
- Services: business rules and cross-entity validation.
- Views: basic input checks; delegate to services.
- Forms: use `forms.Form`/`forms.ModelForm`, clear errors, reuse model validation.
- Always return expected service errors on validation failure.
- Avoid duplicate validation across layers.

## Testing (Pytest)
- Stack: pytest 9.x, pytest-django 4.11+, pytest-cov, Faker (pt_BR).
- Settings: `DJANGO_SETTINGS_MODULE=config.settings.development`, `pythonpath=["src"]`.
- Strategy (priority order):
  1. Services (happy + error paths for all services).
  2. End-to-end view flows.
  3. Template smoke tests.
- Prefer testing services over views when choosing.
- Tests live in `src/<app>/tests/` and `src/core/tests/`.
- Naming:
  - Files: `test_*.py`.
  - Functions: `test_<action>_<scenario>()` (snake_case).
  - Classes: `Test<Context>` (PascalCase).
  - Fixtures: snake_case.
- Use `@pytest.mark.django_db` only when touching the DB.

## Lint and Format
- Run `just lint` and `just format` before push.
- Use `# noqa` sparingly and locally, with brief justification on the same line.
- Prefer `contextlib.suppress(...)` for ignored exceptions.
- If lint flags C901 due to simple guard clauses, allow `# noqa: C901`.
- If conditions are complex, extract to model/service method.
- Reduce nesting when it harms readability; refactor to keep control flow clear.

## Architecture Reminders
- Apps in `src/cadastros` and `src/eleicoes`; shared utilities in `src/core`.
- Shared templates in `src/templates`; project static in `static/`.
- Services are the single business-rule entry point.
- Database access is encapsulated by model methods.
